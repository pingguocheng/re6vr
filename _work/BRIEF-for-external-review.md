# RE6 VR mod 项目简报（给外部评审用）

> 用途：把项目现状、已实测的硬事实、待决问题讲清楚，让没有上下文的人也能给出技术意见。
> 约定：**MEASURED = 在本机实测过**；**INFERRED = 推断/外部资料**。请按这个区分采信。

## 0. 一句话

自制的《生化危机 6》(PC 2012, 32 位 DirectX 9, Capcom **MT Framework 2**) VR mod。
**头部旋转追踪已经工作**（3DOF「三脚架」：眼位固定，只做水平 yaw + 俯仰，绝不 roll），
画面是**铺满显示屏的影院模式**（单画面，无立体）。
现在要做**真 6DOF（头部平移）**；而**「每帧产出两只眼」的立体渲染在本机已判定不可达**（原因见 §5）。

## 1. 运行环境（很多结论的边界都在这里）

- 游戏：RE6 Steam 版 `BH6.exe`；32 位 PE，**LAA 已置位**（MEASURED，PE `Characteristics=0x0123`）；
  D3D9 设备 `3840×2160 / A8R8G8B8 / flags=0x44`（含 `D3DCREATE_MULTITHREADED`）。
- 头显链路：Quest + **Virtual Desktop 串流**，OpenXR 运行时是 VD 的；
  同一进程里 `VirtualDesktop.LibOVRRT32_1.dll` 曾 7 次在游戏退出时崩 `c0000409`（控制局也一样）。
- 显卡驱动：NVIDIA 32.0.16.1664。
- mod 形态：`d3d9.dll` 代理（劫持 `Direct3DCreate9` 导出 + patch 返回的 vtable）、MinHook 内联 hook、
  自建 D3D11 设备把画面提交给 OpenXR。

## 3. 真 6DOF 缺什么：不是要开新通路，而是接线

1. **传位置**：桥（`openxr_bridge.cpp:5375`）目前只把 3×3 旋转交给相机侧 → 需新增头部位置通道。
2. **注入平移的写入点已经存在**：现有「每眼 IPD 偏移」就是"同一向量同时加给 eye 和 target"
   （`cam_steer.cpp:781-786`）→ 平移可直接复用，且已被证明**不累积**。
3. **平移量的单位是错的**：IPD 以"米"读入后**直接当世界单位**用（`0.063 m` → 写入 `0.03 单位` ≈ 0.3 mm），
   因为世界是厘米尺度 → **差 100 倍**。这是真 bug。
4. **F9 语义**：现在只重取角度参考，需同时重取**位置参考**（站立原点）。

**外部源码级对照（做法高度一致）**：
- REFramework（RE Engine）：`pos = game_cam_pos + game_cam_rot * (rot_offset * (hmd_pos - standing_origin))`，
  每帧写、渲染后 `restore_camera()` 还原；`m_positional_tracking` 只门控平移。
- Source 引擎：`pViewMiddle->origin = ...`（平移写在**中眼/单眼**视图上，双眼由它派生）；
  `vr_translation_limit` 默认 **10 单位**硬夹；`vr_projection_znear_multiplier` 默认 **0.3**；躯干 roll/pitch 显式清零。
- Doom 3 BFG VR：`vr_clipPositional`（夹住平移）、`vr_blink`（头撞墙黑屏）、颈部模型 `vr_nodalX/Z`。

**要点**：追踪空间→相机空间的映射**只用 yaw**（用全 pitch 会有"吊臂"效应：低头把相机往前推）；
平移幅度**夹在 0.3–0.5 m**；**投影矩阵与 fov 完全不动**。

## 4. 一个容易被忽略的前提：画面怎么呈现

当前是"虚拟空间里一块屏"（4.0 m 远，张角 59.8°×35.8°，而头显 FOV 是 78.2°×81.4°）。
**屏不铺满视野时，注入平移会读成「电视里的画面在滑」，而不是「我在动」。**
要让平移读起来像 6DOF，需要把屏铺满视野（`re6vr_screen_scale.txt`）——这是**与平移互相独立的另一个变量**。

## 5. 立体（每帧两只眼）为什么在本机判定不可达

十局对照：`stereo=0` 三种配置活了 **65 s / 65 s / 2.5 min**；`stereo=1` 六局**全部**在 **0.4–4 s** 内崩。

- 崩溃签名：`nvwgf2um.dll+0x24678a`（c0000005 **空指针读**）4 局；`d3d11.dll+0x198b74` 2 局；
  **均伴随 LiveKernelEvent 141（GPU 引擎挂起）**；**我们的代码没崩**（SEH 守卫零触发）→ 故障在驱动/运行时内部。
- 已逐条排除：双 pass、眼偏移（`ipd=0` 也崩）、回读次数、帧中取帧。
- 已澄清一个常见误解：**运行时看不到我们那两张纹理**——两眼是同一张 `shared-array` 交换链的两个 slice，
  我们的每眼纹理只被自己的 quad draw 采样。所以差异**全在 mod 这一侧**。
- 候选机制：① 我们的设备调用与引擎自己的命令流语义交织（`MULTITHREADED` 只保证 API 级串行）；
  ② 4K 下多一套图像链的资源/重命名压力（每眼 2492×1401 ≈ 14 MB，交换链 6×27 MB）；
  ③ VD 运行时自身就不稳。
- **三个从未跑过的判别实验**：把抓帧降到 640×360；两套链都建但两眼都绑 eye 0 的 SRV；加内存探针
  （`GetProcessMemoryInfo` + `GetAvailableTextureMem`）。

## 6. 外部调研：有没有现成答案可抄？——基本没有

- **不存在 RE6 的 VR mod**。RE 系 VR mod（REFramework / praydog）**只支持 RE Engine**，MT Framework 一作都不支持；
  中文圈"RE 系列 VR 一键安装器支持 6DoF"指的是 RE2/3/4/7/8/9 + **体感控制器输入**，与 RE6 无关。
- **但同引擎家族（DMC4，DX9/32 位）有现成的相机覆盖做法**：用引擎自带 `uFreeCamera`，
  把某个 viewport 的 `mpCamera` 换成它，然后**每帧只写 pos/up/target**，矩阵由引擎自己算
  （从不写 view/proj 矩阵，也从不改 fov/near/far）。**RE6 里这套零件我们已定位**（见 §2 末行），
  换相机的落点 = 槽记录 `+0x04`。
- MT Framework **没有 Lua**（本机实测：`BH6.exe` 里 Lua C-API 字符串 **0 命中**）。
  `.ahc` / `CAMtrack*.fsm` 确实是相机数据，但**与玩法耦合**（删掉会让伙伴 AI 寻路在特定桥段失效）→ 不要碰。
- 深度重投影（VorpX Z 模式 / SuperDepth3D 一类）**给不了真 6DOF**：只能做几厘米级的时域重投影，
  遮挡区在单帧里根本不存在可用像素（1D 水平近似对立体够用，对平移不够）。

## 7. 待决问题（希望外部意见就这几条）

- **A. 要不要动「眼睛位置」**：用户先前明确要的是 3DOF 三脚架（眼位固定）。头部平移与它直接冲突，
  这是**设计变更**，不是 bug 修复。
- **B. 先走哪条**：
  (a) 最小改动——单画面 + 夹住的 yaw 映射平移（分 4 步，前两步零风险：只传不写 → 固定 20 单位 → 接真数据）；
  (b) 先做"引擎原生自由相机 + 换视口相机"的**纯离线**调研（架构更干净，且是将来做立体唯一正确的形状）；
  (c) 只先修那个 100 倍单位 bug 并复测 IPD。
- **C. 呈现顺序**：先铺满视野，还是先做平移？（两者独立，但先后决定"第一眼观感"）
- **D. 竖直分量是否纳入**（坐着时头的上下浮动是真信息，但会改变相机与角色/掩体的关系）。
- **E. 立体那三个判别实验值不值得跑**（成本低，但即便跑出结果，也只是解释驱动崩溃，不会改变"立体不做"的判断）。

## 8. 本项目的工作方式约束（会限制可接受的建议）

- **不在 live 路径上"改一处、试一局"地迭代**：先用离线/观测模式取证，每次只改一个变量，改动前先定方向。
- 每个结论必须能在日志或二进制里找到证据；"看起来对"不算——本项目已因弱判据付出过 5 次代价
  （例如："形状像 view 矩阵"被当成"是相机"、把 fov 的弧度/度搞混导致整个探针静默失效）。
- 外部资料只在给出出处时才采信，且**实测优先于反推**（已有实例：外部由"社区流行打 4GB 补丁"
  反推 BH6.exe 不是 LAA，本机读 PE 头证明它**是** LAA）。
